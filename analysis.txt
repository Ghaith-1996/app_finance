PORTFOLIOSIGNAL REPO ANALYSIS
=============================

Purpose of this file
--------------------
This file is a plain-text handoff dossier for another AI or engineer. It documents
what the repository currently does, how the system is organized, how data moves
through it, what external services it depends on, and where the rough edges are.
It is intentionally based on the code as it exists in the repo today, not on a
polished or idealized product description.


1. PROJECT IDENTITY
-------------------

What the project is
- PortfolioSignal is a Next.js App Router application for portfolio-aware
  financial workflows.
- The core idea is: ingest market/news data, connect it to a user portfolio,
  run AI analysis, and present a personalized feed plus portfolio insights.
- The repo mixes two modes:
  - marketing/demo surfaces that sell the product concept
  - authenticated product flows that use Supabase-backed portfolio/news data

What problem it is trying to solve
- Investors see too much undifferentiated market information.
- The product tries to filter general financial news through what the user
  actually owns.
- It also tries to turn raw news into portfolio-language explanations:
  why it matters, which holdings connect to it, what the signal stack is,
  and what to read next.

Current product posture in the repo
- This is not a finished production application.
- It is closer to a functional frontend-heavy MVP with real backend/data
  plumbing for portfolios, news ingestion, analysis, and article chat.
- The codebase contains both production-like flows and some demo/static
  content and placeholder messaging.


2. RUNTIME STACK AND ARCHITECTURE
---------------------------------

Primary stack
- Next.js 16 App Router
- React 19
- TypeScript
- Tailwind CSS 4
- Supabase for auth, database, and realtime
- Python worker for news ingestion
- Vitest + Testing Library for frontend and route-level tests

High-level architecture
- Browser/client components handle:
  - interactive onboarding
  - feed filtering and article detail UI
  - analysis trigger/polling
  - article chat interaction
- Server components handle:
  - authenticated page shells and data loading for portfolio, analysis, feed
- Server actions handle:
  - CSV parsing preview flow
  - holdings save/merge/update flows
  - portfolio reads and derived overview data
- API routes handle:
  - feed reads
  - analysis run state
  - refresh/cron/health/ingest news pipeline endpoints
  - article chat thread/message I/O
- Python handles:
  - EDGAR and NewsAPI ingestion
  - normalization and dedupe/upsert into Supabase

Important boundaries
- News ingestion is hybrid:
  - Python fetches/upserts raw articles
  - TypeScript/Node enriches them with AI
- Analysis is TypeScript-only and portfolio-aware.
- Market/news storage is global in `news_items`.
- Portfolio-specific feed rows live in `feed_items`.

Behavior

  - polls run status
  - subscribes to Supabase realtime updates on `analysis_runs`

  2. AI-enrich newly inserted articles
  3. run portfolio-specific analysis

Pipeline stage concepts shown in UI

- enrichment
- analysis

  - queued
  - processing_holdings
  - mapping_news
  - generating_insights

Behavior

  - market: source, category, recency
- Article detail panel shows:

3.7 Article chat
Main entrypoints
- `components/app/article-chat-panel.tsx`
- `app/api/article-chat/route.ts`
- `supabase/migrations/006_article_chat.sql`

Behavior
- Inline chat opens from the article detail panel.
- Chat is per `user + portfolio + article`.
- GET loads or lazily creates a thread.
- POST stores the user message, builds prompt context, gets an AI answer,
  stores assistant reply, then returns the thread.

Prompt context includes
- selected article metadata and summary
- raw article content if available
- stock tags and ticker impacts
- portfolio holdings
- latest feed-item context for that article if it exists:
  - why it matters
  - relevance score
  - matched holdings
- recent conversation history

Critical caveat
- This feature depends on migration `006_article_chat.sql` being applied in the
  target Supabase environment. The route and UI can exist in the repo even if
  the tables are not yet present in a deployed database.


4. DATA MODEL AND STORAGE
-------------------------

Primary tables from migrations
- `portfolios`
  - one portfolio per user entry, contains name/source/sync metadata
- `holdings`
  - portfolio positions and position metadata
- `analysis_runs`
  - track analysis status/progress over time
- `news_items`
  - global ingested market/news pool
- `feed_items`
  - portfolio-specific scored news rows derived from `news_items`
- `portfolio_insights`
  - AI-generated summary/insight cards for a run
- `article_chat_threads`
  - persistent per-user per-portfolio per-article chat thread
- `article_chat_messages`
  - ordered messages within a thread

Important schema evolution
- `001_initial_schema.sql`
  - creates portfolios, holdings, analysis_runs, news_items, feed_items,
    portfolio_insights, base RLS, and realtime publications
- `002_holdings_position_fields.sql`
  - adds quantity, average_cost, cost basis/current value style fields
- `003_portfolio_source_csv.sql`
  - adds CSV/import source support
- `004_news_classification.sql`
  - adds news classification fields and feed match metadata
- `005_news_source_fields.sql`
  - adds source_type, external_id, category_hint, metadata, source confidence
- `006_article_chat.sql`
  - adds article chat persistence tables and policies

Important relationships
- `portfolios.user_id -> auth.users.id`
- `holdings.portfolio_id -> portfolios.id`
- `analysis_runs.portfolio_id -> portfolios.id`
- `feed_items.analysis_run_id -> analysis_runs.id`
- `feed_items.news_item_id -> news_items.id`
- `portfolio_insights.analysis_run_id -> analysis_runs.id`
- `article_chat_threads.portfolio_id -> portfolios.id`
- `article_chat_threads.news_item_id -> news_items.id`
- `article_chat_messages.thread_id -> article_chat_threads.id`

Important indexing and dedupe
- `news_items` has a unique index on `(source_type, external_id)` when
  `external_id` is present.
- `news_items.published_at` is indexed for time-window reads.
- `stock_tags` and `matched_stock_tags` are GIN-indexed.
- article chat thread uniqueness is enforced on
  `(user_id, portfolio_id, news_item_id)`.

RLS model
- Portfolio-owned data is restricted by portfolio ownership.
- `news_items` are readable by authenticated users.
- `article_chat_threads` and `article_chat_messages` are limited to the owning
  authenticated user.


5. NEWS INGESTION AND ANALYSIS PIPELINE
---------------------------------------

5.1 Global news pool concept
- The app now treats `news_items` as a global 24-hour news pool.
- The user portfolio is not used to decide which headline articles to ingest.
- The portfolio is used later, during analysis, to score and filter the stored pool.

5.2 Refresh route
Main entrypoint
- `app/api/news/refresh/route.ts`

Behavior
- Authenticated, portfolio-specific route.
- Validates selected portfolio and requires holdings.
- Resolves global ticker universe from all holdings in the DB for EDGAR.
- Calls Python worker for:
  - EDGAR filings (ticker-based)
  - NewsAPI business/market headlines (global, non-ticker-specific)
- Runs AI enrichment on newly inserted rows.
- Computes a 24-hour news pool snapshot.
- Runs portfolio-specific analysis.
- Returns:
  - stage results
  - ingest breakdown
  - enrichment count
  - analysis run ID
  - pool snapshot
  - analysis metadata

5.3 Cron route
Main entrypoint
- `app/api/news/cron/route.ts`

Behavior
- Secured with `CRON_SECRET`.
- Does unattended ingestion only.
- Does not run portfolio analysis or create `feed_items`.
- Used to keep the global news pool warm/current.

5.4 Ingest route
Main entrypoint
- `app/api/news/ingest/route.ts`

Behavior
- Another authenticated ingestion endpoint that triggers global ingestion +
  enrichment, but not portfolio analysis.
- This overlaps with the cron/refresh surface and is worth noting as part of
  the current repo state.

5.5 Health route
Main entrypoint
- `app/api/news/health/route.ts`

Behavior
- Runs the Python worker in `--check` mode.
- Verifies Python availability and required worker configuration.
- Returns 200 or 503 depending on aggregate health.

5.6 Python worker
Main entrypoints
- `workers/news_ingestion/main.py`
- `workers/news_ingestion/fetchers/edgar_fetcher.py`
- `workers/news_ingestion/fetchers/newsapi_fetcher.py`
- `workers/news_ingestion/upsert.py`
- `workers/news_ingestion/bootstrap.py`

Behavior
- Loads env from `.env` if available.
- Performs preflight checks for:
  - edgartools
  - newsapi-python
  - supabase-py
  - EDGAR identity
  - NewsAPI key
  - service role key
  - writable EDGAR cache directory
- Fetches:
  - EDGAR filings for a provided ticker list
  - NewsAPI global business/market headlines for the lookback window
- Normalizes articles into a shared schema.
- Upserts them into Supabase with per-source dedupe on external IDs.
- Returns structured source breakdown and ingest summary.

Current ingest semantics
- If sources return no rows in the lookback window: "empty"
- If rows fetched are all duplicates: also represented as "empty" with duplicate detail
- If inserted > 0: success or partial
- If both sources fail: failed

5.7 AI enrichment
Main entrypoint
- `lib/services/news/ingest.ts`

Behavior
- Runs after Python insertion.
- Selects recent `news_items` with `global_summary IS NULL`.
- Calls AI article analysis.
- Fills:
  - category
  - stock_tags
  - global_summary
  - overall_effect
  - ticker_impacts

Provider trust rules
- EDGAR stock tags are treated as authoritative.
- Non-EDGAR tags can be extended or adjusted by AI.

5.8 Pool snapshot logic
Main entrypoint
- `lib/services/news/pool-snapshot.ts`

Behavior
- Computes the current stored 24-hour pool in the DB.
- Returns:
  - total pool count
  - latest published timestamp
  - optional counts by source type
- This is used to separate "no new fetch this run" from "no currently available news."

5.9 Portfolio-specific analysis
Main entrypoint
- `lib/services/analysis.ts`

Behavior
- Creates an `analysis_run`.
- Loads holdings for the portfolio.
- Reads the newest 100 `news_items` from the last 24 hours.
- Computes:
  - pool size in DB
  - latest published article in the pool
  - number of candidates scored
- Generates portfolio insights from the article pool.
- Scores every candidate against the portfolio.
- Adds EDGAR source boost.
- Persists only rows with boosted relevance >= 60 as `feed_items`.
- Writes `portfolio_insights`.
- Returns metadata:
  - poolCount24h
  - latestPublishedAt24h
  - candidatesScored
  - feedItemsCreated

Important scoring behavior
- There is no generic fallback feed anymore.
- If nothing meets threshold, the personal feed can be empty even if the market pool is not.
- Matching logic still derives matched holdings/tags/sectors for persisted feed items.


6. AI SUBSYSTEM
---------------

Main entrypoints
- `lib/services/ai/provider.ts`
- `lib/services/ai/index.ts`
- `lib/services/ai/prompts.ts`
- `lib/services/ai/openai-provider.ts`

Provider abstraction
- `getAIProvider()` selects provider from `AI_PROVIDER`.
- Supported provider adapters:
  - OpenAI
  - Anthropic
  - OpenRouter
- If keys are missing, the code falls back to deterministic stub logic.

Prompt families currently present
- article enrichment / classification
- article summary
- sentiment scoring
- portfolio relevance scoring
- why-it-matters
- portfolio insights generation
- article chat prompt

Article chat behavior
- Prompt is article-specific and portfolio-aware.
- It is allowed to use broader financial knowledge.
- It is supposed to distinguish article facts from broader reasoning.

Current caveats
- Stub behavior is simplistic and not fidelity-matched to production AI.
- Providers are called directly via HTTP fetch; there is no queueing, retry
  orchestration, or streaming layer.
- OpenRouter is the default fallback when `AI_PROVIDER` is not `"openai"` or `"anthropic"`.

11. CURRENT REPO-STATE CAVEATS AND ROUGH EDGES
----------------------------------------------

Source-of-truth issues
- `README.md` is still the generic create-next-app template and should not be
  treated as a source of truth for the project.

Product vs repo reality mismatches
- Marketing copy is more polished and aspirational than some backend/runtime details.
- Some pages imply a more complete secure broker-sync product than what is
  actually implemented in this repo.

News pipeline rough edges
- There are overlapping ingest entrypoints:
  - refresh
  - cron
  - ingest
- This is functional, but it means the ingestion surface is not fully simplified.
- `lib/services/news/marketaux-provider.ts` still exists even though the active
  pipeline is EDGAR + NewsAPI.
- Historical source labels such as `yfinance`, `marketaux`, and `seed` still
  appear in types or snapshot helper code, even though they are not all active
  in the current ingest workflow.

Article chat caveats
- The route and UI exist in the repo, but working end-to-end requires migration
  `006_article_chat.sql` to be applied.
- This chat is article-scoped, not a general portfolio assistant.

Feed/analysis semantics caveats
- Personal feed emptiness can mean:
  - no current news pool
  - no articles qualified for the portfolio
  - filters removed all visible items
- The repo has logic to improve this distinction, but these UX semantics are
  still an active area of refinement.

Data freshness caveats
- Portfolio value display can use live Yahoo quotes while broader portfolio/feed
  data can still be based on previously ingested or analyzed DB state.
- Analysis is based on the stored 24-hour pool, not necessarily only on rows
  inserted during the most recent refresh click.

Operational caveats
- Python worker execution depends on local/runtime Python availability plus
  required packages and env vars.
- There is no queue, worker orchestration service, or job retry system beyond
  direct subprocess execution from routes.

13. USE THIS CONTEXT FOR ANOTHER AI
-----------------------------------

Highest-signal facts another AI should retain
- This repo is a portfolio-aware finance app with real Supabase-backed product
  flows and a polished marketing shell.
- The central architectural split is:
  - global news storage in `news_items`
  - portfolio-specific feed derivation in `feed_items`
- News ingestion is hybrid:
  - Python fetches EDGAR + NewsAPI and upserts raw rows
  - TypeScript enriches with AI and runs portfolio analysis
- Analysis scores the newest 100 articles from the last 24 hours and only
  persists feed rows with relevance >= 60.
- Personal feed is not raw news; it is the output of the latest completed
  analysis run for a portfolio.
- Market feed reads directly from the global news pool.
- Auth is Supabase OAuth with middleware-protected routes.
- Onboarding/import and symbol resolution are real flows, not just mocks.
- Article chat exists and is article-scoped plus portfolio-aware, but depends
  on the latest migration being applied.
- The repo contains active product code plus residual/older modules and some
  aspirational copy, so another AI should trust current route/service code and
  migrations more than the marketing language or README.
